# LMC-5 记忆实现对照与改造方案

评估日期：2026-09-13。结论：可以参考 LMC-5 的实现逻辑，在 Libra 现有后端内重构记忆模块；建议采用它的五维组织方式、事实版本和多通道联想机制，保留我们的来源校验、任务事务和聊天/电话分段。

本次完成源码审阅、实现对照和验证，没有修改业务代码或迁移真实记忆数据。

## 1. 它真正实现了什么

LMC-5 的五轴不是五个模型，也不要求五套数据库，而是同一记忆的不同组织和使用维度：

| 维度 | 代码中的核心机制 | 对 Libra 的意义 |
| --- | --- | --- |
| X：时间与主线 | thread、事件块、周/月叙事索引、时间意图 | 同一件事跨天发展时，能从早期计划找到后续结果 |
| Y：关系 | 有类型的记忆边、两跳扩展、较严格的第二跳阈值 | 从“面试”联想到准备、安慰、结果，而不只找词相似的摘要 |
| Z：事实演变 | fact_key、active_fact、current/review/superseded、冲突审计 | 区分“以前住哪里”和“现在住哪里”，旧事实保留历史身份 |
| E：体验信号 | valence/arousal、回应倾向、主 AI 作者和初始优先级 | 区分发生了什么与左然如何理解这次互动 |
| M：维护 | 分类衰减、保护、使用记录、巡检与整理建议 | 控制记忆增长、冗余和浮现频率，并发现断链 |

它有两套不同完整度的实现：SQLite 核心与 PostgreSQL 扩展。核心更适合阅读数据约束；扩展更值得参考召回、后台整理与体验记忆的组织方式。没有必要为了学习这些逻辑就换 PostgreSQL。

主流程可以概括为：原始事件 → 分块 → 提议候选 → 校验并写入 → 建关系/检查事实变化 → 多通道召回 → 按证据用途注入对话。

注意：这是可接线的参考实现。许多算法依赖调用方提供持久化、邻居搜索、模型和调度回调，运行一个类并不等于整套系统自动成立。

## 2. 我们当前的实际差距

### 2.1 写入基础值得保留

`ingestion.py` 已有来源去重、聊天/电话流隔离、话题边界、结束边界和处理进度。`extraction.py` 已有任务租约、重试、整批事务、版本检查、逐条 claims 原文引用检查、用户事实来源约束，以及 discard/recent_only/long_term 的价值判断。

这些适合我们的中文陪伴场景。改成 LMC-5 风格不需要撤掉它们，也不需要把所有对话先积压到晚上才处理。

### 2.2 更新候选过度依赖“最近”

`MemoryExtractionMixin.job_input()` 先取最近更新的 80 条活动事件，再用词面重合排序，最终提供 12 条候选。纠错检查也只看最近 80 条。

因此旧事件一旦掉出这个窗口，即使新消息确实是它的后续，模型也可能看不到更新目标。这是根据候选获取代码推导出的风险，并非已经测得的线上错误率。

改法：先按稳定事件身份、事实键和已确认实体定位，再补充 FTS/向量候选，最后限制候选数量。限制应落在相关候选集上，而不是先截掉历史。

### 2.3 事件身份不等于事实身份

当前 `event_identity` 适合识别同一具体事件，`memory_revisions` 适合保留编辑历史；两者不能完整替代跨事件的事实演变。

例如“用户搬家”是新事件；“用户当前住址”是被这个事件改变的事实。建议给明确、可追踪的事实添加独立稳定键，例如 `(subject_id, predicate, scope)`，事实值另存，不能把 value 算进用于识别同一个事实槽的键。

当前新状态不会通过一个独立 Z 流程稳定地找到旧状态。被移除的旧演化实现曾支持显式 supersession，但不应当作当前能力。

### 2.4 Y 轴当前没有完整写入和读取闭环

最新 `recall.py` 仍接收 `graph_hops`，但已没有原来的图扩展循环；`context.timeline()` 返回空 links/open_loops。旧关系表的存在不代表关系召回仍启用。

建议新建独立关系任务：事件提交成功后触发近邻检索和逐对关系判断。无需先生成 story 才能建立两条事件之间的联系。

### 2.5 情绪召回入口存在，记忆坐标写入缺失

`recall.py` 会读取 `episode_details.affect_json` 的 valence/arousal；当前 `extraction.py` 的 INSERT/UPDATE 没有写这个字段，仓库业务代码搜索也未找到对它的补写。测试中的人工构造坐标不能证明正常对话链路已经打通。

此外，本地 query 坐标来自关键词表，不能可靠区分否定、引用和混合情绪。应优先复用现有 affect 流程的、带事件来源的结果，而不是再造互不一致的情绪判断器。

要分别记录用户报告的情绪、左然的体验表达、系统推断及其来源。用户的难过不能自动成为左然的亲身经历；后台模型也不能凭空给左然写永久人格结论。

### 2.6 原文救援过窄

当前原文检索只在主召回完全为空、查询不超过 40 字时运行，并扫描最近 500 条未被任何 memory_sources 引用的原文。

两个容易漏的情形：主召回有一条普通命中，但用户问的专名只在原文中；原文已被某条摘要引用，但摘要恰好省略了被问的细节。

可参考 LMC-5：把短专名/引号精确检索作为独立的小额度通道，同时保留原文作为定位证据的标记。已提取原文也可以定位，但须检查来源有效性、后续更正和当前事实版本。

### 2.7 当前日历层是索引摘要

`calendar.py` 已有日/周/月/季/年投影和来源版本追踪。`_summary()` 主要是按时间拼接并截断，不是识别跨事件变化的叙事模型。

可以先用于导航；若确实需要“这段时间发生了怎样的变化”，再增加可回溯的叙事摘要。摘要不能变成新的独立事实证据。

## 3. 参考代码中不能照搬的部分

**NightDream 的证据闸门不够完整。** 提示词要求逐字引用，但通用 `extract/gate` 主要检查格式、重要性、risk 和来源列表非空，没有在这里验证引用是否真存在、来源 ID 是否属于输入。自定义 writer 可以加强检查，因此这个发现针对通用层，不代表所有部署都没有防护。

最小验证：实际传入 chunk 1，候选引用不存在的 chunk 999，evidence 填写输入中不存在的文本；`run(apply=False)` 仍返回 1 条 promoted。我们的逐条 evidence_quote + experience_id 校验必须保留。

**关系构建会丢失方向。** `NightDream.build_relations()` 给邻居套用候选的首个安全 relation_hint，并把端点按 `min(id), max(id)` 排序。验证中新记忆 10 对邻居 2 的 derived_from 被交给 writer 为 `(2, 10, 'derived_from', 0.5, ...)`。端点大小无法决定派生或时间方向；更不能用一个 hint 证明所有邻居的关系。

应按关系对生成证据、方向和置信度。对称关系才规范化端点；时间/派生关系保留语义方向。关系用于联想时也不能被当作因果证明。

**阈值需要按我们的数据校准。** 默认按文本长度过滤短 chunk、重要性阈值和语义去重可能漏掉“别再这样叫我”这类短而重要的表达。高相似度也可能对应明确否定或状态反转，不能直接当重复丢掉。

**体验优先级不能代替真实性。** E 轴“主 AI 创作体验、后台只能提议”的分工值得借鉴，但主 AI 写出的事件陈述仍需来源验证。初始优先级、情绪强度和事实置信度应分开。

**自发浮现需要适配对话。** `perception.py` 是高活力加随机采样，适合提供“可能想起的事”；对 Libra 应加入近期重复、当前话题、未完成事项和用户边界判断。先作为内部候选，是否提起由对话策略决定，不直接触发消息发送。

**不照搬使用次数强化和固定最高分。** `ob_score()` 的 protected 固定高分、hit_count 加权可能使同一记忆长期占位。保护应保障保存；是否召回仍需相关性判断。上下文选中、回复实际使用、新证据确认应该分别计数。

**不复制部署外壳。** Claude Code hooks、Forge/Swap、VPS cron 和它的 persona 特定格式不必引入。用我们的 worker、事件来源和应用启动流程完成同等职责即可。

## 4. 建议的本地重构形态

保留 `MemoryStore.recall/context` 和现有 API 外壳，内部增加清晰的数据关系与任务类型。以下是拟议结构，不是已实现内容：

| 部分 | 建议落点 | 关键约束 |
| --- | --- | --- |
| X：具体事件主线 | 事件所属主线与阶段元数据 | 领域主线与聊天 session/thread 分开；存报告时间与实际发生时间 |
| Z：明确事实版本 | facts / fact_versions / conflict proposals | 稳定事实键；current/historical/review；来源、适用范围和版本前置检查 |
| Y：事件关系 | 独立 relations 模块与后台任务 | 逐对证据、类型、方向、来源版本；第二跳限量；不经过失效来源 |
| E：体验记录 | experiences 模块，对接 affect 与主回复结果 | 作者、来源事件、初始优先级、情绪坐标和不确定性分别保存 |
| M：维护 | maintenance 任务 | 先补索引、查孤立边、查冲突、去重提议；衰减与保护另行明确规则 |
| 召回 | 拆分 recall 通道与统一组装 | 主事实、原文导航、关联线索分层；共享有效性过滤；各通道独立降级 |

不建议用五个新的大型生成器替代旧演化链。X/Y/Z 多数工作是围绕明确事件和事实组织数据；M 可以先做确定性维护。只有需要语义判断的环节才调用模型。

一个完整例子：用户说“下周面试”，之后说“准备得有点紧张”，最后说“拿到 offer 了”。应该保存不同日期的真实事件，把它们连为同一面试主线，更新这次事项的当前阶段，并保留原来的紧张是过去状态。之后聊到新工作时可关联这个过程，但不能继续把用户描述为仍在等待面试。

## 5. 实施顺序与验收

1. **固定基线、定义兼容迁移。** 先完成当前正在进行的移除工作并更新对应测试；在数据库副本上迁移，不重写原始聊天和来源 ID。旧表只作为兼容档案，不自动把旧推断升级为新事实。
2. **先实现 Z 和更好的写入候选搜索。** 明确事实槽、版本、冲突状态；解决最近 80 条窗口问题。新事实被确认替换时，在同一事务中更新当前指针、版本和索引失效状态。模糊矛盾只生成待核对提议。
3. **实现 Y 的写入—读取闭环。** 新事件触发独立关系任务；候选搜索后逐对判断；两跳召回返回关联路径。任务租约、重试、幂等和来源修订失效规则继续沿用现有做法。
4. **改造召回分层及原文通道。** 先过滤失效/越界候选，再统一排名和预算。保留中文 FTS 与向量互补，是否改成严格级联要通过对照测试决定，不机械照搬 0.45/0.30 阈值。
5. **打通 E，再加入有限自发浮现。** 新体验从可追踪的主回复/affect 结果写入；不让后台补造过去体验。浮现不绕过当前用户表达，不挤占主事实预算。
6. **最后补 M 与叙事索引。** 独立记录上次成功运行、积压量和失败原因；不要让向量服务失败阻塞事实写入。保留随时可从原始来源重建索引的能力。

必须覆盖的验收场景：

- 100 条以上新事件之后，仍能找到并更新早期同一事件。
- 同一人新旧住址、已完成/未完成计划并存时，只把适用版本当当前事实。
- 不同日期重复发生的同类事件不会被相似度去重误删。
- 主召回已有命中时，仍能找回原文中的中文专名和被摘要省略的细节。
- 图边可解释、方向正确；来源失效或修订后不会继续传播旧结论。
- 从真实输入到情绪写入再到召回完成端到端测试，而不只人工插入 affect_json。
- 重复召回不凭空提高事实置信度；用户明确纠正优先。
- 聊天/电话队列、事务回滚、重启恢复、预算和来源权限不退化。

对比指标应包括：旧事实误用率、事实纠正命中率、跨日期事件召回率、无关记忆注入率、重复提及率、模型调用量和召回延迟。参考项目单元测试通过不能证明会比我们线上效果更好。

## 6. 本次验证结果与限制

- 固定版本 LMC-5 测试：`167 passed, 4 skipped`。没有连接真实 PostgreSQL，也没有运行真实模型质量评测。
- 完成上文两个最小验证：不存在的证据被通用候选闸门放行；有方向关系的端点被按 ID 重排。
- 本地首次所选 99 项测试在并发修改期间得到 `87 failed, 12 passed`，主要停在暂时缺失的 `memory_archive.sql` 初始化处；之后文件已经出现，因此这个结果不能描述稳定版本。
- 再次运行时旧演化测试因 `domains.memory.evolution` 已移除而无法收集。
- 不含该文件的六个测试模块随后得到 `67 passed, 5 failed`，失败涉及被移除的生命周期、实体/图相关旧预期。测试文件也在变化，不能把这些结果当作干净的版本基线，更不能归因于本次评估。

本次只新增这份说明；业务代码修改、迁移和真实对话评测均尚未实施。
