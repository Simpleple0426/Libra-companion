# Libra Agent / 归然：项目与简历说明

更新：2026-10-06。以下描述依据当前仓库实现；功能实现与效果验证分别说明。

## 项目定位

本地优先的有状态 AI 陪伴系统，使用 Flutter Android 客户端和 Python/FastAPI 后端，将多轮聊天、长期记忆、情绪状态和生活规划连接在同一应用中。手机承担交互与媒体上传，个人电脑运行后端并通过模型 CLI 调用模型服务；聊天、记忆及生活状态在本地持久化。模型服务仍可能需要网络，不能将其描述为完全离线推理。

面向后端 / Agent 开发岗位，推荐名称：**Libra（归然）｜有状态 AI 陪伴系统后端**。简历重点为聊天 Agent、长期记忆、生活执行、持久化与评测；客户端由 AI 辅助完成，用于交互演示，不列入个人技术栈和核心贡献。

## 整个项目的结构

| 部分 | 当前实现 | 关键代码 |
|---|---|---|
| 客户端与服务 | Flutter 聊天界面，文字、图片和语音消息入口，FastAPI 服务，消息更新查询 | `mobile/lib/screens/chat_page.dart`、`backend/app/runtime.py` |
| 聊天 Agent | 在主聊天会话中按需查询个人记忆、角色知识、原文、生活状态和天气；工具结果进入后续回复；查询阶段限制轮数和调用数 | `backend/application/main_chat_agent.py`、`chat_research.py` |
| 情绪处理 | 并行处理本轮情绪，最终回复前等待结果；失败时采用已有状态并记录降级，阻止未取得情绪结果的提前回复 | `backend/application/chat_emotion.py` |
| 长期记忆 | 原始记录、分段、候选提取、证据校验、正式记忆及事实版本；FTS5、向量、关系图等召回，RRF 融合；保留来源和作用域约束 | `backend/domains/memory/lmc.py`、`lmc_recall.py`、`backend/application/memory_segmentation.py` |
| 生活 Agent | 持久消息输入、任务调度、模型工具循环、日程和陪伴操作、宿主校验、事务提交和结果通知 | `backend/application/local_life.py`、`backend/life_prototype/autonomous_agent.py` |
| 回合可靠性与追踪 | 回复校验、持久化投递记录、后置任务和回合查询；生活侧 inbox/outbox、消息去重和重启恢复 | `backend/application/turn_pipeline.py`、`life_agent_mailbox.py`、`life_agent_events.py`、`backend/app/api/trace.py` |
| 扩展交互 | 自习、阅读、影音、日历、动态、日记、信件等应用界面与业务模块 | `mobile/lib/screens/`、`backend/application/` |

聊天与生活是相互连接的两条执行链：用户输入可以提交生活请求，生活提交结果可以进入聊天上下文。最终聊天回复通过聊天 Agent 和回复校验链路生成；当前生活评测只验证到聊天上下文回执。

## 简历版本：建议直接使用

**Libra（归然）｜有状态 AI 陪伴系统后端**  
技术栈：Python、FastAPI、Uvicorn、SQLite / FTS5、FastEmbed（ONNX）、混合检索 / RRF、LLM 工具调用、JSON Schema、Skill 路由、Codex CLI / Claude Code

按能力展开：后端服务（Python / FastAPI / Uvicorn）、数据存储（SQLite 与事务）、检索（FTS5 / FastEmbed 本地向量 / 关系图 / RRF）、Agent（工具调用 / JSON Schema / SKILL.md / 技能路由）、可靠性（持久消息队列 / 幂等 / 重启恢复 / 回合追踪）、验证（unittest / 隔离合成世界 / 真实模型评测）。简历空间有限时只保留上面的技术栈行，机制细节放在项目条目里。

- 构建基于 FastAPI 的 AI 陪伴系统后端，实现主聊天会话中的按需工具查询，结合长期记忆、生活状态和并行情绪处理生成回复，并对回复进行校验与持久化投递。
- 实现基于 SQLite 的长期记忆链路，覆盖对话分段、候选提取、证据校验及事实版本管理；融合 FTS5、向量与关系图召回，通过 RRF 排序，并保留来源追踪和作用域过滤。
- 实现生活规划 Agent，以 SKILL.md 与技能路由组织阅读、工作、用餐等活动执行模块，将自然语言请求转为日程和陪伴操作；通过宿主校验、事务提交、持久化 inbox/outbox 和消息幂等支持运行时重启恢复，将执行回执提供给聊天上下文。
- 构建覆盖聊天工具调用、长期记忆检索、生活执行及跨链路回复的 54 场景分项评测，结合数据库状态断言、消息关联校验与自动语义评审，验证事实纠正、来源隔离、查询超时及持久化恢复；区分任务执行成功与回复一致性，定位模型漏传工具必填字段等失败。

## 面试讲述

一分钟介绍：

> 这是一个有状态 AI 陪伴系统后端，把聊天、长期记忆和生活规划连接起来：聊天 Agent 可以按需查记忆和状态，生活 Agent 可以执行受校验约束的日程操作，执行结果再进入聊天上下文。工程上的重点是持久化、消息幂等、回复校验、回合追踪和真实模型评测。评测中发现两次修改状态都保存成功，但第二条通知因展示文案合并而丢失，将通知去重改为按提交 ID 后，原失败场景各重复三次全部通过。客户端由 AI 辅助完成，用于交互演示，我的求职重点是后端与 Agent。

讲述中“我”的实现范围应与自己的实际贡献一致。

被问到 AI 使用情况时，说明客户端由 AI 辅助完成，并按实际情况说明后端也使用了哪些 AI 辅助。个人贡献可围绕需求定义、架构取舍、代码理解、集成验证和问题定位展开，只保留自己实际参与且能解释的部分；不把 AI 生成的代码描述为全部手写。

### Skill 与 MCP 的表述依据

- Skill 已有实际实现：`backend/life_prototype/skills/` 存放 SKILL.md，`skill_router.py` 根据活动选择执行模块，部分模块读取技能说明。可以写“Skill 路由与模块化执行”，不将所有活动模块描述为由模型动态加载文档。
- 仓库包含 MCP 相关第三方组件，但名称不等于当前调用协议。豆瓣适配器调用 `douban-mcp-cli` 的 JSON CLI，音乐后端调用本地 HTTP 服务；共读组件带有 MCP server 文件，仅凭文件存在无法证明当前应用通过 MCP 调用它。
- 生活模型适配器显式设置 `mcp_servers={}`，工具由宿主程序执行。当前简历不将 MCP 列为已实现的核心技术；可以准确描述为“第三方工具的 CLI / HTTP 适配与集成”。这不涉及开发工具自身是否支持 MCP。

建议准备三个可演示案例：

1. 聊天查证：用户询问既往偏好或具体事实，展示 Agent 检索、原文证据和回复过程。
2. 状态执行：先安排阅读，再改成休息，展示日程变化、两条关联通知和聊天读取到的执行回执。
3. 恢复与排错：展示同一消息重复投递、重开运行时，以及通知丢失问题的修复前后证据。

记忆和聊天演示使用合成数据；演示结果不自动成为量化效果指标。

## 已有验证证据与边界

- 30 场景首轮复核为 28/30：29 条有效原始结果，加 1 条修正初始地点后的单独复测。这是历史复核汇总，非同一版本完整重跑。
- 修复后的两个原失败场景，固定请求模型 `gpt-5.6-sol`、reasoning `medium`，各重复三次，6/6 通过。共 12 轮消息的状态提交及关联通知断言通过。
- 与本次通知修复相关的本地回归测试 39 项通过；不是整个仓库全部测试的通过数量。
- 2026-10-06 分项基线：聊天 12/12、记忆检索 8/8、生活执行 29/30、跨链路任务 3/4。共 54 场景，各重复一次。17 条最终回复的自动语义初评均有据，未发现虚报成功；未进行人工语义标注，不能称为聊天泛化准确率。
- 两条任务失败涉及模型漏传生活操作必填字段，宿主拒绝提交；跨链路失败的回复准确说明尚未生效。任务失败仍保留，不能以回复准确替代任务成功。
- 生产模块组合现已覆盖最终聊天回复和实际记忆召回；记忆提取模型、情绪判断、多模态质量、真实第三方服务、HTTP 与移动端整条链路仍未由本次评测验证。
- 记忆检索正例仅 6 条，Recall@4 与 MRR@4 均为 1.0，样本过小，不建议作为简历效果亮点。没有可用于简历的泛化幻觉率、成本下降或延迟改善数字。
- “本地优先”指数据与应用运行方式，模型 CLI 仍连接模型服务；不能写成纯本地模型或完全离线应用。
- 项目实现了聊天 Agent、生活 Agent 等专门执行链，不据此宣称通用多 Agent 协作框架。
- LMC 记忆设计参考上游架构，采用本项目的 SQLite 和模型接口实现；面试时说明参考来源与自己的实现范围。
