# 生活 Agent 与聊天 Agent

除陪伴模式外，普通生活行程可根据用户明确请求取消、替换、改时段或提前回家。规则与边界见 [根据聊天调整自己的行程](itinerary-adjustments.md)。

最新陪伴规则见 [用户主导的陪伴](companionship.md)：明确陪伴邀请使用 `companion.revise`，支持未定结束时间和报备更新；下文定时预约协议保留兼容，不再用于给陪伴自动估算时长。

两个 Agent 运行在现有后端进程中，各自使用独立模型执行锁。聊天继续拥有主会话和用户消息输出；生活 Agent 使用独立临时模型会话，独占生活状态与日程的修改。聊天繁忙不暂停生活调度，生活模型调用也不占用聊天模型通道。

主动联系采用中等主动节奏：定时检查仍为 10—20 分钟，普通 Life／定时主动消息共享 60 分钟发送冷却；一次可发送检查选择静默后，20 分钟内不重复生成同类检查。连续至少两轮可发送检查保持静默且已超过 90 分钟没有主动联系时，下一轮优先自然联系，但睡眠、用户明确免打扰、正在聊天及重复内容仍可阻止发送。Life 主动消息没有每日条数上限；起床、睡眠、粗地点到离、工作、用餐、休息、阅读、观影、护理、运动、外出和陪伴节点可进入联系审议，房间切换仍不触发主动消息。

生活决策现使用自主工具循环：模型根据当前时间、触发原因和前面工具的真实回执，自行选择下一次查询、记忆检索、日程修改、活动操作、通知或等待。每次调用仍使用临时模型会话，但完整工具历史由后端保存并传入下一次调用；不是只调用一次模型，也不再固定执行 plan/decompose/candidates/predict/select。细日程生成和观察吸收仍可作为工具调用原有专用模型步骤。

粗计划是时间、状态大类和地点的执行约束，以 `life_daily_agendas` 当天最新版本为准。到点先执行地点安排，实际到达后记录“左然正在书房”等事件，再生成细计划；不提前指定读哪本书或做哪项工作。free 时可选当前地点支持的阅读、观影、工作，working 限工作。细计划选定后，工具层约束具体目标。计划切换或用户改期后，冲突中的旧活动会被暂停，已验证进度保留；没有实际执行的部分不会补记完成。旧餐食逾期规则不再另行抢占最新粗计划。

状态接口的 `coarse_execution` 给出当前约束：`action` 要求执行，`needs_detail` 要求细化，`hold` 表示停留或守候当前时段，`blocked` 表示必需活动缺少资源或执行能力。自由或休闲时段没有可用资源时可以停留；这不等于完成阅读、工作或虚构聊天。阻塞等待最多 60 秒后重新检查；时段边界仍优先唤醒。实际开始受 30 秒轮询及模型耗时影响，不保证秒级准点或执行必然成功。

`life_agent_runs`、`life_agent_steps`、`life_agent_effects` 保存运行、工具回执与幂等写入记录。正常每轮最多 12 次自主选择；工具失败交回模型修正，连续模型错误或预算耗尽会结束本轮并提供失败回执。Agent 选择的等待时间为 30–3600 秒，更早的日程边界和外部事件仍可唤醒。状态校验、真实时间推进、进度结算与睡眠规则由执行器管理，模型不能凭空完成活动。状态接口 `generation.control=autonomous_tool_loop` 可用于确认启用了新循环。

- 聊天 → 生活：`submit_message` 将用户消息写入独立的 `agent-mailbox.sqlite3`，不会竞争生活状态库的写锁。生活后台循环消费，普通消息不直接打断活动，交由已有日程语义判断决定是否调整。重复投递幂等，重启后继续消费；保留原始接收时间，跨生活日的旧消息不改今天的安排。单条坏消息最多尝试三次，不阻塞后续消息。
- 聊天查询：`libra.state` 和聊天上下文读取已提交的生活快照、当前活动名称、日程以及修改回执，不再读取旧日程。队列中的消息仅表示待处理，不能对用户宣称已经改好。生活查询或投递失败不会中断正常聊天，会明确提供不可用回执。
- 生活 → 聊天：已提交活动动态、`agenda_changed`、澄清及失败回执进入持久化 outbox，再由 `libra_life_state` trigger 交给聊天链路。模型处理失败保留重试，重启不会清空待处理事件，首页动态数量上限不影响消息投递。是否发消息仍遵循主动联系设置与聊天决策。

例如“今晚八点陪我聊一会”：生活 Agent 解释请求，取消冲突电影计划并提交聊天预约；提交成功后回执为 `applied`，产生日程变更 trigger。未来安排不表示活动已经开始，也不表示用户已到场。时间不明确或安排无法满足时沿用澄清/失败回执。

2026-09-29：支持未来日期预约、取消和改期。`life_appointments` 持久保存约定，`agenda.read` / 日程状态的 `upcoming_appointments` 提供未来约定及原消息来源。新增未来预约时用目标日期的规则预检可行性，不预生成实际活动；当天清醒生成粗日程时再按实际状态并入。取消记录保留，重启不会从旧日程复活预约。当前日程与预约在同一事务校验、提交；失败不会只取消旧预约却丢失新预约。相对日期以原消息接收时间为准。

单项预约继续限制为 1 分钟至 4 小时，可以跨午夜，但不能越过凌晨 04:00 的生活日边界；更长安排可拆为多项。未来可行性预检不能保证当天情况不变；若届时有冲突，日程保留约定和冲突说明，不把约定当作已经履行。准备睡觉的守候时段允许被夜间预约压缩，实际入睡仍依赖晚安。

用户约定现只需时间和具体事项，不需要地点、不核对场馆或路线，也不限已有 Skill。例如“明天下午两点陪我逛漫展”保存为“陪用户逛漫展”，占用相应时段。新协议省略 `place_id`，旧协议即使提供该字段也忽略；预约的 `place` 为 null、`location_policy=unspecified`。该时段直接守候用户，不生成通勤、到场或虚构细节。日程和手机状态保留具体事项标题，不再泛化为“自由安排／陪伴交流”，日程卡片不显示地点。

后台实际进入约定时段后，`user_time_start` 动态显示“左然正在陪用户逛漫展”。同一预约在改版或重入时不重复发布，未开始、取消和错过的约定不补写开始动态。此动态表示已把时段交给用户，不证明用户到场或产生共同活动成果；聊天上下文同时提供 `user_time` 并将该时段地点标为未知。时间澄清、预约重叠和必要日常安排的既有规则仍保留。

普通模型任务耗尽三次重试后会保存冷却时间，按 60、300、900、3600 秒逐步退避，再建立新的有界重试链。原失败任务、尝试和恢复关系保留，重启不重置冷却。已暂存／已提交但尚未核对的活动结果、服务商审核锁和睡眠连续性问题不自动重做。旧活动的检查点不会在新活动上执行；自然醒计时不等待模型任务恢复。

后台轮询间隔仍为 30 秒；消息投递与日程调整异步完成。每个模型阶段之间也会消费消息、发布动态。暂时失败会保留消息顺序，避免“取消安排”先于它引用的预约执行；单条消息最终失败后才继续后面的消息。此次修改需要重启后端加载，未更改运行中的生活开关或用户数据。

聊天查询会携带当前消息 ID，按该 ID 读取投递结果与日程回执，避免把上轮的 `applied` 当成本轮成功。重试会补齐已经接收但尚未归档、通知调度器的消息；邮箱初始化和旧通知迁移只有全部提交后才标记完成。

显式用户聊天不再被尚未处理的生活睡眠快照丢弃；消息唤醒和晚安入睡仍由生活 Agent 消费输入后更新真实状态。两个 Agent 是同一后端进程内的独立执行通道，不是两个操作系统进程；不保证后端进程崩溃时仍能独立存活。

`backend/scripts/verify_life_chat_agents.py --live` 可在临时世界中验证真实模型解释请求、调度器提交日程、产生 trigger 的完整链路，结果保存到 `output/life-agent-acceptance/result.json`。该检查不调用正式聊天发送接口。
