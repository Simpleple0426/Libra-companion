# 左然生活运行流程与数据设计

状态：设计草案 v1。尚未实现新生活系统，未启动后台模拟，未迁移数据库。本文的接口名和数据结构是拟议契约，不代表已有实现。

## 1. 已确认的目标与尚未决定的内容

已确认：
- 已婚同居；精简人物描述与习惯沿用[人物稿](../character/左然初始人物设定_精简候选稿.md)，核心人格与处事方式保持固定。
- 跟随现实日期与时间；不替用户生成行动、对话、决定，不从未回复推断用户状态。
- 场景沿用[家庭](../character/左然家庭空间与物品清单.md)、[律所](../character/左然律所空间与物品清单.md)、[城市](../character/左然城市地点清单.md)清单。
- 废弃旧规则日程和旧模板生活生成方式。聊天记忆使用 LMC，左然自身生活记忆参考小镇。
- 实际活动可中断并保存进度；聊天能影响计划；可以感到挫败，但不产生长期心理影响，不改变核心人格和处事方式；外部后果可以持续。不要求固定的情绪恢复时限。
- 已确认以 D2A 为基础替代旧情绪计算，聊天与生活共用统一状态；属于适配重构，尚未实施。

已补充确认：睡眠仍由用户晚安触发；困倦与睡前准备不自动等于入睡。D2A 候选行动选择不能绕过这项约束。

唤醒方式已确认：睡眠有大致的自然结束时间；睡着时收到用户消息会醒来，左然知道自己先前正在睡觉、此次是被消息叫醒。起床时间参考旧规则：普通工作日约 07:00、工作日已安排晨泳时约 06:30、周末约 07:30，原规则允许上下浮动 5 分钟。被叫醒后需要用户再次说晚安才续睡。此为用户交互需求，不是 D2A 原版机制。

仍待决定：D2A 维度选择与迁移映射、离线补算、初始事项、首批 NPC、出差范围、正式启用时刻。以下“建议”不得据此转成已确认设定。时区暂建议沿用 Asia/Shanghai。

## 3. 总体流程

```text
现实时间 / 新观察 / 用户消息 / 活动到期
                  ↓
       按事件时间取得一致状态
                  ↓
       结算已有行动的实际进展
                  ↓
  更新角色可知观察与 D2A 统一状态
                  ↓
读取固定人设 + 相关记忆 + 未完成事项 + 粗计划
                  ↓
     继续当前行动，或提出候选活动
                  ↓
  预测后果 → 选择 → 校验 → 提交行动
                  ↓
   世界推进产生结果与可知观察
                  ↓
  保存事实、进度、记忆；必要时反思及重规划
```

该流程是 G1–G3、D1–D2、C1 的组合设计，不是原代码调用顺序的逐行复制。原小镇 move 顺序为 perceive→retrieve→plan→reflect→execute；D2A 源码在下一次 pre-act 更新上一步结果。此处将结果结算显式化，以处理最终一步、聊天中断和重启。

### 一次推进的具体步骤

| 步骤 | 读取 | 产物与约束 | 依据 |
|---|---|---|---|
| 1. 接收触发 | 当前时间、事件队列、已处理时间 | 去重后取得到期事件；未来事件不提前当作事实 | A、U |
| 2. 结算活动 | 当前行动、经过时间、可验证结果 | 仅提交实际进度；失败或尚未完成不发放预测收益 | C1、D2 + A |
| 3. 形成观察 | 世界结果、角色知情范围 | 世界发生不等于左然知道；用户未知状态保持未知 | C1、U |
| 4. 更新内在状态 | 上次更新时刻、已结算结果 | 每段时间和每个结果只更新一次 | D2 + A |
| 5. 检索与计划 | 当前问题、生活记忆、LMC 引用、待办 | 当天粗计划；需要时细分近期活动 | G1、G2 + A |
| 6. 选择行动 | 人格、承诺、计划、需求、观察 | 保留继续当前活动选项；重大新信息才考虑打断 | D1、G1 + A |
| 7. 校验与提交 | 候选、前提、版本 | 合法候选之一；不凭模型文本直接改数据库 | A |
| 8. 安排后续 | 行动检查点、期限、待处理事件 | 保存下次触发时间；必要时反思 | G3 + A |

活动的预计结束时间用于安排检查，不保证届时一定成功。新发现、资源不足、聊天和工作变化可能引起中断或延期。

## 4. 现实时间调度

建议独立生活调度器，不依附聊天请求或主动消息开关。当前 [runtime.py](../../backend/app/runtime.py) 的 _checkin_loop 每 30 秒检查旧日程，部分生活处理位于 proactive_enabled 判断后；切换时需拆开这些职责。

建议：
- 持久化 next_due_at；活动检查点、需要处理的观察、承诺期限和用户消息可唤起推进。
- 没有新情况时继续活动，不每分钟让模型重新决定人生。后台轮询间隔不等于认知调用频率。
- 新一天产生计划时，先承接跨午夜活动及未完成事项；不在日切时清空睡眠、阅读或任务进度。
- 使用带时区时间，存储 UTC 时间戳并明确显示时区；事件时间、处理时间分开记录。
- 系统时钟回拨不产生负时长；时钟大幅前跳进入恢复处理，不直接将一整天活动标为完成。
- 计划只预生成意图与粗时间段，不能提前生成几天已经发生的经历。
- 生活开关与主动消息开关独立。用户不聊天可继续生活，不代表必须主动发消息；通知策略另定。

需求劣化需按模拟经过时间计步。D2A 原版每步一次概率抽样；在不同步长或停机跨度下直接抽样一次会改变行为。建议采用持久化的固定需求子步、随机种子及已处理游标，具体步长通过原型验证后确定。不能把轮询次数当作需求流逝。

## 5. 拟议数据结构

建议优先复用项目已有 SQLite 基础设施，为新生活数据增加独立命名的结构；这是建议，不是已选定数据库迁移。下表为逻辑实体，未必一项对应一张表。

| 实体 | 关键字段 | 写入与语义 |
|---|---|---|
| PersonaSpec | actor_id、version、核心描述、原则、确认来源 | 运行中只读；用户修订另增版本 |
| Place / Object | id、parent_id、名称、用途、位置、可用状态、来源 | 场景初始配置；物品移动更新位置，不复制身份 |
| WorldFact | id、subject、内容、valid_time、来源事件、revision | 已提交的模拟世界事实；不混入候选预测 |
| Observation | id、actor_id、event_id、observed_at、内容、知情依据 | 角色可知信息；不读取未知世界内幕 |
| LifeEvent | id、类型、发生时间、记录时间、来源、因果引用、payload | 追加记录；更正以新事件说明，不静默改历史 |
| Plan / PlanItem | id、version、时间窗、目的、约束、状态、依据引用 | 计划意图；修改仅影响未发生部分 |
| Activity | id、计划引用、类型、位置、开始/检查时间、状态、前提、revision | 一次执行实例；拟定→进行→完成/中断/失败 |
| OngoingTask | id、目标、依据、已完成部分、下一步、期限、状态 | 跨多个行动继续；一次失败不自动删除任务 |
| Progress | actor_id、task_id、内容版本、已提交位置、结果引用 | 实际进度；阅读按书籍内容版本定位 |
| NeedState | actor_id、dimension、value、updated_through、last_result_id、版本 | 每个维度只有一个负责更新的系统 |
| StateSnapshotRef | actor_id、state_revision、有效时间 | 聊天与生活引用同一 D2A 状态快照，不保留独立的旧情绪计算 |
| LifeMemory | id、kind、created_at、last_accessed、描述、importance、embedding_ref、证据引用 | 小镇式个人记忆；事件、计划、反思语义分开 |
| SourceRef / Commitment | source_system、source_id、source_revision、承诺内容、状态 | 连接聊天证据与安排，不复制成两段独立经历 |
| Step / Outbox | step_id、expected_revision、阶段、结果、重试状态、幂等键 | 事务、故障恢复、记忆/情绪异步投递 |

数据不变量：
- 左然同一时刻只有一个主要身体活动；设备运行可并行。短消息处理作为注意力事件，长谈是否中断由实际处理决定。
- 用户动作必须引用用户提供的依据；邀请不能写为共同活动已发生。
- 计划、预测、角色观察、世界事实与反思必须可区分。
- 核心人格不能由计划器、世界裁定器、反思器写入。
- 每项状态变化可追溯到源事件；有记忆不代表事实正确，反思是推断。
- last_accessed 必须保存，避免小镇公开代码中的重启丢失问题。
- 不以 expiration 字段存在就宣称实现了自动遗忘；过期与历史保留策略另定。

## 6. 拟议模块接口

以下为框架无关的契约，后续再映射到 Concordia 组件或项目服务。Concordia 的接入版本与现有模型适配器尚需兼容验证。

```text
read_snapshot(actor_id, event_time) -> Snapshot(revision, observed_through)
observe(snapshot, committed_events) -> Observation[]
retrieve(context, life_query, chat_query?) -> EvidenceBundle
plan(context, evidence, pending_tasks) -> PlanProposal
propose_actions(context, plan, needs) -> Candidate[]
predict(candidate, context) -> Forecast
select(context, candidates, forecasts) -> Selection(candidate_id, reason)
validate(selection, snapshot) -> ValidatedAction | Rejection
resolve(activity, checkpoint, world_snapshot) -> OutcomeProposal
commit(step_id, expected_revision, outcome) -> Receipt | Conflict
reflect(observation_refs, memory_refs) -> ReflectionProposal
```

每个模型输出包含使用的输入版本与证据引用；结构错误、缺前提、非法地点、替用户行动均拒绝写入。Forecast 永不写入实际进度或已发生记忆。涉及世界约束的选择失败可有限重试，不能无限生成直到得到想要的成功结果。

完整人格、承诺与当前计划需要进入最终选择，不仅进入候选提出阶段；这是针对 D2A 最终选择上下文缺失的适配。

## 7. 世界推进与持续活动

按 C1 分开“左然想做”和“世界结果”。第一版可将已定义设备、移动、阅读进度等交给结构化处理；需要文本模拟的工作互动交给带前提和证据的世界裁定器。两者职责划分属于 A。

- 不能因写了“处理案件”就自动生成完整胜诉过程。工作事项必须有当前材料、目标和实际推进结果。
- 阅读应基于已提供的书籍内容或片段；可访问内容之外不得编造书中事实。模型调用成功也不等于现实时间已经读完。
- 建议阅读按片段提交进度，只有达到对应活动检查点并完成内容处理才推进；中断保留最后已提交位置，半段状态另存。
- 阅读内容处理失败时不推进位置，明确待恢复；避免无限重读或跳章。书籍完成有明确状态。
- 当前 [reading.py](../../backend/domains/content/reading.py) 的 advance 是已有共读进度入口；新自主阅读建议按 actor_id、书籍和内容版本分开记录，避免自动消费用户共读进度。
- 设备结束可发生在后续活动期间；洗碗机运行不要求左然一直站在厨房。
- 无法确认的世界结果保留未知或待处理；不为了让生活看起来热闹而生成事件模板。

## 8. 聊天如何改变计划

建议流程：
1. 用户消息先按聊天系统保存，LMC 保留来源。原始消息与已经整理的 LMC 记忆区分，不能假定记忆提炼立即完成。
2. 取消息时刻的一致生活快照。若后台落后，只读取已提交状态，并显式保留时间缺口。
3. 聊天可以读取相关生活事实；若提出“早点回家”，生成带消息引用的变更请求。
4. 左然结合未完成工作、承诺、通勤和当前状态决定答应、协商或拒绝，不无条件执行。
5. 答应时先提交计划变更与承诺，再生成成功表述；若并发冲突或提交失败，重新判断，不能先说改好了。
6. 发给用户的回复通过持久化发送队列投递；回复未送达与承诺已经提交分别记录，重试不重复承诺。
7. 新阻碍保留事件和承诺状态，重新处理后续计划；不能让聊天承诺和后台行为长期分离。

明确时间的短期约定需有即时持久化记录，不仅依赖 LMC 重要性阈值筛选。SourceRef 指向真实消息，LMC 派生记忆可随后关联；此桥接属于适配，不改变用户聊天记忆由 LMC 管理的决定。

收到较晚的消息不倒改已经提交的历史，按处理时可行性调整未来。长时间聊天与活动中断的时间核算也只计一次。

## 9. 两套记忆的接口

- 用户聊天内容与其记忆仍归 LMC；生活观察和反思归小镇式记忆。
- 一次邀约的聊天来源只保存一份，通过引用进入计划；实际赴约的自身行动是之后的新生活事件，二者不是重复拷贝。
- 用户指出旧信息错误时，按源版本标记关联结论需复核；不把修改过的旧聊天继续当作有效依据。历史行为仍保留“当时依据什么做出”。
- NPC 对话建议归生活 chat/event，但这是待确认的归属选择，不静默扩大 LMC 的范围。
- 纪念物品来历标注“用户设定的初始背景”，不伪造赠礼日期或新增一次赠礼事件。
- 检索建议先以小镇论文的时间近期性、重要性、相关性等权为基准，并单独保留即时观察的关键词检索入口；不复刻公开代码反向排序等疑点。权重选择仍需原型评估。
- 反思引用真实依据，不能将一次挫败概括成永久人格变化。拒绝写核心字段只是必要条件，还需检查反思文本对后续行为的影响。

## 10. D2A 统一状态替代旧情绪系统（已确认方向）

维度、聊天接入与迁移建议已细化为[D2A 统一状态与迁移设计](左然D2A统一状态与迁移设计.md)。该文的具体参数与适配仍是草案，不代表替代已经实施。

用户已确认以 D2A 为基础替代旧情绪计算，聊天表达与生活行动读取同一套状态。此前“保留现有事件情绪、另加 D2A 需求”的建议不再作为目标方案。

- 身体需求与心理状态采用 D2A 的维度描述、行动/观察更新与候选比较机制，依据 D1、D2。
- 事件原因与经历由记忆保存，聊天结合状态与相关记忆表达具体感受，不凭空增加独立情绪数值。
- D2A 原版有愉悦度、安全感等维度，没有独立覆盖全部挫败、担心等情绪；是否扩展维度须说明依据，不能称为原版已有。
- 用户要求是会感到挫败但不产生长期心理影响，不是要求固定时限恢复。因此不预设继承旧半衰期，也不以新增定时恢复公式作为替换前提。
- 固定人格、处事原则及反思边界继续有效；长期状态与记忆对行为的影响需要验证，不能仅凭核心字段只读就保证符合要求。

现有 [emotion_v1.json](../../backend/config/emotion_v1.json) 的 connection、closeness、reassurance、care、expression、autonomy 不直接逐项复制为 D2A 维度。维度选择、初值、旧历史是否仅归档、旧状态映射与体力/疲劳属性归属仍待设计；当前不随意指定数值。

工程适配包括聊天事件更新、状态持久化、版本化快照、消费者与 UI 接口迁移。可复用旧队列、租约和去重设施，但不保留另一套并行更新的旧情绪计算。原型比较可隔离运行，正式切换后只有一个有效状态来源。

状态更新异步完成时，决策记录使用的 state_revision；更新失败保持最后可靠快照并标记待处理，不假装已生效。D2A 合理性检查达到重试上限仍接受数值的原码行为不直接照搬，建议拒绝未经通过的更新。具体恢复与降级属于工程适配。

## 11. 并发与持久化

建议每个角色只有一个状态提交入口。模型推理在事务外进行：

1. 读取 revision 与输入快照，保存待处理 step。
2. 推理并保存候选结果；不持有长时间数据库写锁。
3. 短事务比较 revision、检查 step 幂等键，原子提交活动、事件、进度、计划修订和 outbox。
4. 若版本变化，重新校验或重算，不覆盖新收到的消息。
5. 向量、生活记忆和情绪消费者按 event_id 去重；投递失败可补做，不能重复执行原行动。
6. 决策检索必须包含已提交但尚未向量化的新观察，避免索引延迟导致失忆。
7. 保存使用的随机种子和已接受结果，重试不重新抽出另一段已经发生的历史。

停在“推理完成但未提交”时可以恢复校验；停在“已提交但未发布”时只补投递。物品状态和阅读进度必须同一结果事务提交，防止书读完却没进度、或反过来。

## 12. 关闭 App 与服务停机的恢复方案

下列是建议方案，尚未成为用户确认的离线策略。

| 情形 | 建议行为 |
|---|---|
| App 关闭，后台服务仍在线 | 按现实时间继续自己的生活；主动发消息由独立设置决定 |
| 短暂后台中断 | 从已提交检查点恢复；可证明的设备到期等结果幂等结算，不自动虚构交流或工作成果 |
| 长时间后台中断 | 记录时间缺口，保存未完成任务；不生成一整段“其实都发生了”的故事 |
| 模型不可用 | 保留最后可靠状态与待处理结果；无需模型的设备状态可推进，需模型裁定的进度不冒充完成 |
| 正在恢复时用户发消息 | 优先处理消息，以已确认状态回答；不等待虚构补齐全天经历 |

长停机后，角色当前活动与位置可能过时，需显式标为“截至上次确认”；不能把旧状态当作实时。建议恢复时用当前时间、已有状态和真实可处理结果重新规划，未裁定的行动转为待恢复，不声称在缺口中一直读书、一直睡觉或已经外出。

如果希望停机期间也形成完整模拟生活，需要另选离线补算政策，说明它是事后模拟并保存来源；本方案未默认授权这项行为。没有常驻后台就无法保证全天实际连续计算。

## 14. 最小原型与验收

实施顺序已细化为最小原型实施清单（历史文档已归档）：建议先做家中闭环，再扩展下述律所与工作事项，最后准备真实接入。该清单尚未执行。

最小原型建议：家和律所、一个可持续工作事项、一本有内容的书，以及已确认的基本身体需求；不要求一次让 106 个地点都生成细节。测试用事项和时间均标为测试，不写进人物真实背景。测试时可使用可控时钟验证一天行为，生产仍跟随现实时间。

| 验收场景 | 应验证的结果 |
|---|---|
| 计划阅读但尚未开始 | 无已读进度，无“读完”记忆 |
| 阅读中收到用户消息 | 不冒充用户行为；按实际需要中断，进度可续 |
| 用户希望早点回家 | 计划/承诺提交成功才回复已调整；后续行为一致 |
| 行动失败 | 不兑现预测需求收益；保存失败及未完成部分 |
| 世界发生未知事件 | 不直接进入左然观察和亲历记忆 |
| 活动跨午夜 | 进度连续，原行动不复制，次日计划承接 |
| 重复事件或提交后崩溃 | 只结算一次，无重复情绪或记忆 |
| 模型输出非法对象或用户台词 | 拒绝写入，有限重试或显式降级 |
| 停机后恢复 | 保留真实检查点和时间缺口，不虚构共同经历 |
| 反思一次失败 | 保留处境变化，不改核心人格或生成长期逃避风格 |
| 关闭主动消息 | 生活调度仍可运行；不因此自动发送消息 |
| 新旧系统切换 | 一个生活写入方，UI 不混读旧未来日程 |

先做状态与事件闭环，再接计划、需求和记忆，最后接聊天与生产读端；每阶段只测对应行为。运行一天并重启是最低验证，不代表已经证明长期稳定。

## 15. 待确认决策与实施前条件

无需用户决定表名、事务或接口等工程细节。需要用户确认的行为选择：
- App 关闭继续生活、长停机保留缺口而不自动补造经历，是否采用上述建议。
- 睡眠已确认晚安触发、有大致自然醒时间、用户消息可唤醒且保留唤醒原因；起床时间参考旧规则，被叫醒后再次晚安才续睡；晚安识别及特殊作息情况仍需细化。
- 已确认以 D2A 替代旧情绪计算；维度选择、初值和旧状态迁移仍需设计。
- 初始情境与 NPC 范围、出差限制等，可按[启动设定](../character/左然生活启动设定.md)逐步确定。

这些选择不阻碍设计和测试支架，但正式运行依赖它们。下一步产物应是可审查的最小原型实施计划与配置样例，而不是未经确认就启动长期模拟。
