# 根据聊天调整自己的行程

聊天对 Life 有两条独立路径：明确邀请陪伴使用 `companion.revise`；早点回家、取消健身、更改活动时段等使用 `agenda.revise.proposal.itinerary_changes`。后者不会创建陪伴会话或“陪用户”预约。

当前支持本生活日剩余时间（到次日凌晨 04:00）的以下修改：

- `cancel`：取消选中的可选活动，重新计算后续通勤。
- `replace`：在明确时段安排另一项已有活动，例如在家阅读、休息、工作、运动或家务。
- `reschedule`：将现有可选活动移到明确的新时段，保留活动和地点。
- `return_home`：以明确时间作为回家出发时间，从实际位置通勤回家；之后安排家中活动及必要用餐、洗漱，不回到原来的外出工作块。

普通分享或关心不自动修改。“早点回家”先协商具体出发时间；“现在回家”可直接提交。活动开始时间与回家出发时间含义不同；要求某时到家时，需计算通勤或进一步澄清。时间、路线、资源不满足时返回 `clarify`，不能声称已修改。

每项字段：`operation,item_id,start_at,end_at,activity,place_id`。取消只填 ID；改期填 ID 和新起止时间；替换填起止时间、活动、地点；回家只填出发时间，其他字段为 null。请求保留最新用户消息引文。相对日期由解释器按原消息接收时间解析。

用餐和洗漱不会被删掉。回家后的未准备餐食可调整为家中用餐；已经准备的异地餐食不能被虚构搬运。与已确认陪伴、预约或约定冲突时需先协商处理，不能覆盖。原定未来时间尚未实际发生，不会记成活动已完成或人已到家。

修改、日程版本和消息回执原子提交，并核对实际状态版本。`user_constraints.itinerary` 保留已确认调整，使同日重启、重新生成日程时继续生效；新请求可覆盖旧的可选安排。移动仍由已有移动执行器逐步执行，阅读/观影等活动沿用原有 Skill。跨天陪伴预约沿用陪伴系统；跨生活日的普通行程调整目前会要求澄清，不能虚报提交成功。

实现：`backend/life_prototype/itinerary_updates.py`；验证：`backend/tests/test_itinerary_updates.py`。自然语言语义判断由模型完成，离线测试验证工具提交与执行约束，不代表所有自然表达均经过真实模型测试。
# 已发送回复与行程承诺

后台读取已提交的聊天回复，对角色自身行程候选（回家、出发、运动、阅读等）重新审议。原用户消息先走原有处理；已应用的修改不重复执行。角色明确答应调整时，Life 可选择可行时间落实，仍受真实路线、必要活动和已确认约定约束。否定、引用、假设由语义审议排除，候选命中本身不代表执行成功。

处理游标持久化，首次启用不追溯旧聊天；这一通路只允许修改自身行程，不授权陪伴或用户预约。陪伴请求继续使用原有链路。当前候选覆盖常见自身行程表达，尚未以真实模型验证所有说法。

“急急急 回家！”“快回家吧”“回家！”可作为立即出发的时间依据，在提交时解析为当前时间，避免模型调用延迟使时间过期。询问、否定、未来日期不按立即出发处理。
