# 用户主导的陪伴

明确要求“陪我……”才进入。普通出行分享不是邀请。具体事项显示“陪用户逛漫展”等，没有事项显示“陪伴用户”。不验证地点，不生成路线、用户位置或共同活动成果。

陪伴期间，Life Agent 使用 `companion.revise` 处理最新报备：出发、到漫展、吃饭等直接更新当前事项；事项结束而下一步未知时改为“陪伴用户”。没有报备就保持当前事项，不因沉默、晚安、App 关闭或跨天结束。

明确开始时间可约到未来，开始时间不明确需澄清。只说“陪我去漫展”“明天陪我”不会默认现在；先询问什么时候出发。明确“现在”或同一事项的近期上下文已确定开始时间时才可提交。补答时间可通过 `context_message_id` 引用原邀请，不必重复整句。结束时间可为空；为空就持续保留，不估算时长，也不强制追问。日程中的当天显示范围不是结束时间，手机显示“结束时间未定”。最新明确截止时间到达后恢复自主规划。

除明确截止时间外，只接受两种自然结束：

- 完整、明确的“不用陪我了”“不需要继续陪我”“结束陪伴”等指令。代码采用保守白名单；“你先忙”“你去忙你的”“接下来我自己来”不自动结束。复杂句不确定时继续陪伴。
- 用户已报备外出同行后，完整、明确的“我到家了”“已经回到家啦”等到家消息。在家陪伴不适用；带继续陪伴请求的消息不得走结束工具。“回家了”可能只是准备回家，不自动结束。

主页、详情页、聊天页在陪伴期间统一显示“陪伴中”，并提供“结束陪伴”按钮。按钮调用 `POST /life-system/companion/{session_id}/end`，不伪造聊天消息。重复结束幂等，旧会话按钮不能结束新会话。

持久数据位于 `life_state.current.companionships`：会话 ID、版本、开始/可空结束时间、当前事项、外出报备状态和结束原因。状态修改、回执和动态在同一事务提交。模型写入必须核对状态版本及最新消息引文，并按消息顺序处理。手动结束后的过期模型提案会被拒绝。

执行器将陪伴作为当前日程覆盖，暂停原自主活动，不生成虚假活动成果。结束递增 `companion_epoch`，按当前时间和实际状态重建剩余日程；不补演错过的活动。阅读/观影等原有活动恢复规则保持现状。

代码入口：`backend/life_prototype/companionship.py`。自然语言含义由 Life Agent 判断，代码负责状态、引文、结束条件和并发校验；离线测试不等同于真实模型对所有说法的识别保证。
