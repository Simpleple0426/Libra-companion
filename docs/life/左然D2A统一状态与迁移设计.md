# 左然 D2A 统一状态与迁移设计

状态：研究与设计草案，尚未实现、迁移或启用。替代方向已经确认；本文的维度选择、更新限制与迁移步骤是供审阅的建议，不自动视为用户已确认。

## 1. 已确认的边界

- D2A 为新的统一状态机制，替代旧情绪计算；聊天和自主生活共享状态。
- 核心人格、处事方式保持不变。可以感到挫败，但不产生长期心理影响；实际失败及其外部后果仍可记住。不要求固定时间清除情绪。
- 现实时间推进；睡眠仍由用户晚安触发，有大致自然醒时间。睡眠中收到用户消息会醒来，并知道自己原本在睡觉、被消息叫醒；起床时间参考旧规则（详见启动设定），被叫醒后必须再次晚安才续睡。
- 只依据用户提供的信息记录用户行动、对话与决定；沉默不等于拒绝、离开或关系变化。
- LMC 保存聊天产生的记忆；左然自身生活经历采用小镇记忆机制。两者引用同一事件时不能重复更新状态。

## 3. 首版维度建议

建议先采用以下 10 个原版维度，保留原英文标识及数值方向；中文名仅用于理解。原版定义比日常中文词更具体，实现时必须保留完整定义，不能只给模型一个名称。

| 维度 | 含义与方向 | 本项目约束 |
|---|---|---|
| hunger / 饥饿 | 0 饱足，10 极饿 | 不把计划吃饭视为已经吃过 |
| thirst / 口渴 | 0 水分充足，10 极渴 | 实际饮水才结算结果 |
| sleepiness / 困倦 | 0 休息充分，10 极度困倦 | 高值不能绕过晚安触发入睡 |
| comfort / 舒适 | 越高越舒适 | 依据身体与环境观察 |
| health / 健康 | 越高越健康 | 数值降低不能单独生成疾病事实 |
| joyfulness / 愉悦 | 越高越愉悦 | 不等于所有情绪的总和 |
| cleanliness / 清洁 | 越高越洁净 | 主要指自身清洁，不等于房屋整洁度 |
| safety / 安全感 | 越高越觉得环境安全 | 不直接代表担心用户或婚姻安全感 |
| spiritual satisfaction / 内在满足 | 越高越有内心满足、平静与意义感 | 不把低值解释为核心价值观改变 |
| social connectivity / 社交联结 | 越高越感到有意义的社会联结 | 不等于夫妻亲密值；也可来自已发生的同事等互动 |

暂不建议启用：

- `passion`：原版定义涉及从懒惰、缺少动力到勤奋，直接使用容易与固定处事方式冲突。暂不加入，也不自行改名为“体力”后称为原版。
- `recognition`、`sense of control`：原版有定义，但是否需要单独追踪，留待工作场景原型验证；控制感不意味着控制用户。
- `sense of superiority`：原版有定义，目前没有用户需求支持启用。

这不是论文规定的最佳组合，也不是已确认的最终配置。先少量维度验证行为是否自然，比复制全部维度后再让用户逐项调参更合适。

## 4. 数值怎样更新

### 原版机制与适配

原版在下一次 pre-act 根据上一步行动与当前观察更新各维度，再施加概率性劣化。行动的预测收益不直接写成实际状态。每个维度变化方向不同，不能统一解释成“越高越需要满足”。

建议把结算变成显式步骤：接收已发生事件 → 取得角色可知观察 → 更新受影响维度 → 校验并保存新版本。这样最后一次活动、聊天打断或服务重启后也能结算，不必等下一次行动生成才处理。

对原版时间劣化，建议作以下明确适配：

- 饥饿、口渴、困倦和自身清洁可在原型中采用有界的时间变化；速率需按现实时间验证，暂不填写生产数值。
- 健康、安全感、愉悦、内在满足、社交联结与舒适，首版建议主要依据可知事件和持续处境更新，不因单纯经过时间就随机推到极端。该限制与原版统一概率劣化不同，是项目建议。
- 用户未回复本身不产生“被拒绝、关系恶化”的观察；后台中断也不等于经历了孤独、危险或生病。
- 同一时间段不能因消息多、读取多而重复计算时间变化。服务停机后如何处理缺口仍待确定，不在这里默认补写生活。

原版速率和目标值由实验配置及特质映射产生，不是已经验证适合左然的心理常数。首版不要为取得这些参数而自动给他增加“胆小”“懒惰”等特质。

### 更新校验

建议每次保存旧值、新值、所依据的事件与观察、更新时间、状态版本及更新规则版本；解释文本是更新依据摘要，不是新增世界事实。模型输出须通过范围、字段、事件归属与重复结算检查。更新失败保留上个有效版本并标记待处理，不编造成功结果。

这些是工程补充：官方代码的合理性检查与有限重试并不能替代上述约束，也没有提供本项目所需的完整状态恢复。

## 5. 聊天如何共用状态

建议流程：

1. 用户消息先作为“左然收到的消息”进入事件流。涉及用户行为时保留消息来源；邀请、愿望、未来计划不转成已完成事实。
2. 与到期生活事件按约定顺序结算，读取同一版本的状态；同一事件只更新一次。
3. 按 D2A 的观察更新思路评估相关维度，而非套用“收到消息必定愉悦 +1”的规则。无关维度可保持不变。
4. 回复生成读取固定人设、当前状态、消息内容和相关记忆。生活规划随后也读取这个状态。
5. 若聊天确实改变约定或活动，另行提交计划变化；说“现在做饭”不等于已经做完并得到收益。
6. LMC 与生活记忆写入使用事件引用。异步记忆提取完成时不再次发放状态变化。

原 D2A 没有为本项目提供这套手机聊天事务，以上是将其观察驱动更新接入现有系统的设计。

### 没有“挫败值”，如何表现挫败

例如一个工作方案未被采纳：记录真实结果及左然知道的原因；模型据此评估是否影响愉悦或内在满足，不规定必然下降几分。回复与下一步行动结合该事件和状态，可以表达挫败并继续处理工作。

不增加隐藏的长期“创伤值”，也不将一次失败反思成“我从此不敢承担责任”。可以保留任务层面的经验、补救事项和外部后果。具体感受是有事件依据的语言表达，不建立第二套独立情绪引擎；也不能声称 D2A 数值本身能完整区分挫败、悲伤与担心。

人格不变不能只靠锁定人物文件。反思、检索结果、候选行动和最终表达都应检查是否把情境感受泛化成稳定人格改变；这是满足用户需求的适配，论文不保证这一点。

## 6. 旧系统怎么迁移

建议采用“历史归档，依据事实初始化”，不做无依据的数值换算。

| 现有内容 | 建议处理 |
|---|---|
| OCC 类情绪、强度、PAD 心境 | 归档保留供回溯，不转换成 D2A 数字，不继续参与新状态计算 |
| connection、closeness、reassurance、care、expression、autonomy | 不与 D2A 强行一一对应；旧亲密需求不等于社交联结 |
| 旧事件、观察及聊天记录 | 保留来源和时间；只抽取仍有效的事实供初始化，不批量重放旧情绪增减 |
| 固定人物设定、婚后关系、已确认物品与来历 | 沿用已确认事实；关系身份不设为会随状态降低的数值 |
| 队列、租约、幂等与版本提交机制 | 评估复用基础设施；改换更新器与数据契约 |
| 旧日程、旧模板生活生成 | 按既定方向停用，不将尚未发生的旧计划转换成人生记忆 |

### 初始化建议

为每个维度分开记录“运行用初始值”和“初始值的依据”。启动时优先使用当时仍有效的事实；资料不足时可用明确标记的原型默认配置，而不是生成一段吃饭、睡眠或社交经历来解释数字。具体默认值与速率须在原型配置审阅中给出，目前不伪装成用户已确定的数字。

旧数据只归档不会自动保留旧系统的即时情绪连续性，这是这种迁移方法的代价。正式切换前需查看初始化快照，确认没有突兀或缺乏依据的极端状态。

### 正式切换步骤建议

1. 先在隔离存储验证新更新器及聊天、生活读取流程，不写真实记忆、不发送消息。
2. 准备旧状态归档、事件处理检查点、新配置及可回退版本。
3. 暂停旧写入器，处理或明确标记未完成事件，生成新状态初始快照。
4. 一次切换状态读写入口；停用旧情绪计算、旧需求触发和旧生活生成。切换期间新消息仍需可靠入队。
5. 校验切换后的唯一写入者、事件边界及消费者版本，再恢复处理。

回退不是把新 D2A 数值倒算回 PAD。若需回退，应停下新写入、保存新阶段记录，恢复已归档旧快照并单独处理切换后的事件；不能重演已发生行为或重复发送回复。实际迁移脚本和回退验证尚未编写。

## 7. 需调整的现有消费端

已核对的入口包括：

- `backend/domains/affect/engine.py`、`service.py`：旧计算与状态服务；后续接入统一更新器和版本状态。
- `backend/domains/affect/expression.py`：当前依赖情绪类别和 PAD，需改成读取 D2A 描述及事件依据，不能伪造 PAD 兼容数值。
- `backend/domains/affect/impulse.py`：旧需求阈值与情绪驱动不能原样沿用。主动消息是可选行动，还应受用户开关及发送约束限制。
- `backend/app/runtime.py`：有 `dominant_emotion`、`affect_state_v1`、旧事件表与表达上下文的读取，需要逐项迁移；缺少旧字段不能永远回退显示“平静”。
- `backend/config/emotion_v1.json` 与旧状态表：用于归档和迁移核对，不作为新参数的自动来源。

前端字段及所有间接依赖仍需实施前完整检索，不能把这份入口列表当作已完成的代码改造清单。若界面继续展示具体情绪词，应标为依据事件生成的描述，不包装成 D2A 原生检测结果。

## 8. 原型验收与下一步

已补充四场景设计走查（历史文档已归档）。这是纸面推演，不是运行测试；其中标明了失败反馈更新对原版提示所需的适配。自然醒与消息唤醒方向已确认，起床时间已按用户要求参考旧规则，续睡已确认需要再次晚安；特殊作息情况仍待细化。

建议下一阶段先形成可审阅的“维度配置 + 事件走查”，再写运行代码。重点检验：

| 场景 | 应满足的结果 |
|---|---|
| 计划做饭，但活动尚未执行 | 不提前改善饥饿 |
| 实际吃饭后重复收到同一结果 | 状态只结算一次 |
| 收到无关消息 | 不强制改变每个维度 |
| 用户长时间未回复 | 不编造用户行为或关系危机 |
| 工作失败及之后再次检索记忆 | 能表达挫败、记住外部后果；不改变核心人格和处事方式 |
| 很困但没有用户晚安 | 不擅自入睡 |
| 活动结束与聊天同时到达 | 使用一致且可追踪的状态版本 |
| 服务重启或最后一步结束 | 已发生结果可恢复、不会重复结算 |

以上尚未执行测试。当前建议先审阅 10 维配置及按事件更新心理维度的适配；不用用户重新填写整套复杂人物模板。完整生活流程见[生活运行流程与数据设计](左然生活运行流程与数据设计.md)。
