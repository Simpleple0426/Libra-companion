# 统一认知回合：实现、验收与边界

初始记录日期：2026-09-05；统一处理契约更新：2026-09-15。本文包含历史实现记录，不代表真实模型质量已经验收。

## 主体结构

### 2026-09-15：当前用户消息统一处理契约

`application/turn_routing.py` 已停止文本分类。所有用户消息与附件均返回
`kind=unified`、`appraisal_mode=full`、`appraisal=true`、`retrieval=true`；
问候、短确认和情绪跟进不再因类别而省略召回或评估。普通与紧凑提示词均保留
传入的设备状态、记忆及当前上下文。统一处理本身不授予工具执行权限。

这样避免分类捷径省略上下文，同时放弃按类别跳过阶段的节省；实际效果、延迟与
成本需要单独测量。`python backend/evals/run_routing_eval.py` 检查标记和提示词
上下文保留契约，不测分类准确率，也不替代真实模型或端到端验收。

下节及后续表格记录 2026-09-05 的实现快照，其中分类、简单消息跳过阶段及
旧模块路径不再代表当前行为；当前用户消息处理契约以上述说明为准。

### 历史记录：2026-09-05 聊天分流与轻量润色调整

- `turn_routing.py` 用本地规则和最近六条消息决定处理范围，不新增分类模型。简单呼唤、问候、确认跳过召回、Appraisal、Need 更新和额外润色模型；短确认若承接明显情绪或冲突，保守走情绪链路。独立归因阶段已移除，关系意义、责任、确定性、可控性和预期变化不再通过额外模型单独生成。
- 普通闲聊、独立工具请求没有明显情绪意义时不更新情绪；工具请求仍走已有工具与权限路径。当前分流是可测试的规则首版，不等同于完整语义理解；普通消息仍保留原有召回。
- 输入事件与原始聊天照常保存；不需评估的事件标记 `committed`，`result_json.appraisal_skipped=true`，并记录 `processing_route`，不假装已执行 Appraisal。不清零既有情绪，时间投影与互动时间继续生效。简单回合的回复事件也不排队更新情绪；其他回复事件不再依据模型自己的表达更新 Need。
- 共同聊天发送出口只做一次可选措辞润色。编辑只允许小改原答，不新增事实、承诺或控制标记；失败、空结果、格式错误、过大改动等保留原答。原答和润色状态可在回合 `response_edit` / `verdict_json` 查看。
- 删除普通聊天的语义拒绝后重生成、固定澄清降级。程序的明确边界、消息格式、记忆 ID、主动联系资格和行动权限检查仍保留；硬检查不通过不发送，不用另一句模板冒充原答。润色不再意味着完成独立事实核验，反馈明确记录 `semantic_validation_performed=false`。
- 电话与发布型内容的独立 `validate` 入口未在此次重构中替换；以下旧版语义校验说明对这些入口仍适用。前端和原主线程机制未改变，需重启后端加载新代码；未调用真实模型验收。

`backend/turn_pipeline.py` 管理回合、权限策略、回应计划、校验、提交与反馈；`turn_actions.py` 提供程序限定的本地操作能力；`main.py` 将既有入口接到这些共同边界。既有 MemoryStore、AffectService 和主会话线程机制保留。

## 两个提交点，而不是把模型调用包进长事务

1. 输入先提交：用户消息/电话原文、事件及来源记录不能因后续回复失败丢失。输入引发的内部状态变化有自身幂等收据。
2. 输出后提交：生成、校验、语音合成等完成后，再短事务提交最终输出及回合收据。

明确本地操作还有单独的“动作 + 结果收据”事务：成功执行的用户请求不会因为回复失败被假装撤销；重试不会重复执行。TTS 文件生成与网络服务不属于 SQLite 事务，崩溃可能留下未引用的媒体文件，不能宣称全系统可一起回滚。

## 已接入的出口

- 普通文本、带图聊天、语音转写回复、表情回复。
- 天气、生活状态、用户状态/动态、待办、打卡、内容发现、定时联系及主动冲动消息。
- 电话：校验先于 TTS，电话记录与回合收据共同提交；不把电话写成主聊天气泡。
- 共读：校验并持久化房间内回复，不混入主聊天消息表。
- 信件、日记、动态、动态评论、自动照片配文：使用共同的发布校验与事务提交。

图片目前没有新增独立的“视觉事实抽取数据库”：附件事件先记录，生成和校验可看原图，视觉解释不自动成为用户事实。工具结果与日历计划也不等于事件已经发生；工具收据不再次触发情绪模型形成循环。

## 本地动作权限

生成回复的 `actions` 字段不再直接执行。当前能力白名单是添加待办、添加习惯、完成待办及打卡，必须由程序识别明确请求，匹配目标后执行。例如：

- `提醒我明天买牛奶`
- `帮我创建一个喝水习惯`
- `帮我把待办买牛奶标记完成`
- `帮我给喝水打卡`

含条件、否定、引述、模糊意愿、时间参数尚不支持或同名目标不唯一时，不自动写入。相较旧聊天动作解析，这里有意收紧了自动操作范围；不能把“我想买……”自动变成待办，也不静默丢弃用户指定的几点几分。原有界面上的待办/打卡操作接口保留。

明确请求保存相册、请求写信等原有业务入口仍保留其独立的用户授权判断；它们不是生成模型获得的新通用工具权限。

## 存储与接口

仍使用 `backend/libra.db`，新增九张回合表：

| 表 | 用途 |
|---|---|
| cognition_turns | 事件、上下文、计划、最终输出、校验及状态 |
| cognition_context_revisions | 上下文版本快照 |
| cognition_delivery | 主聊天/电话/房间/发布渠道的可获取状态 |
| cognition_post_jobs | 持久化后台认知任务 |
| cognition_feedback | 校验与反馈记录，不自动强化 |
| cognition_actions | 明确本地操作与结果收据 |
| cognition_inputs | 文本聊天请求去重 |
| cognition_call_inputs | 电话输入去重，保留首次转写 |
| cognition_notifications | 主动消息的通知 outbox |

`GET /cognition/turns/{turn_id}` 可查看回合、状态、投递及后台任务；`POST /cognition/turns/{turn_id}/retry-post` 仅重试失败的后台任务。

`POST /cognition/turns/{turn_id}/feedback` 接受 `{message_id, accepted, comment}`，必须关联存在的用户消息；不会直接强化记忆。

文本 `/chat` 新增可选 `request_id`，同一 ID / 同一输入返回已有结果，冲突返回 409；省略时每次请求视为新输入，不能区分网络重试和用户真的重复说话。前端本次未改，因此还不能声称当前客户端已实现端到端请求去重。电话使用已有 `call_id + turn_id`，同一音频重试不重复保存输入或应用情绪。

## 投递语义与恢复

- `available` 表示消息已持久化，可供客户端轮询；不是已读或认可。
- 主动通知先在事务内创建 outbox；已有业务调用和后台补发共用原子领取，最多启动一次外部推送尝试。
- `sent` 只表示推送服务返回成功，不表示设备显示、用户阅读或接受。
- 结果不确定记为 `unknown`，不自动重发；进程在推送中退出可能留下 `attempting`，同样不能判定成功或自动重发。未尝试的通知超过 15 分钟过期，不补发陈旧打扰。
- 无配置等情况记为 `unavailable`。消息本身仍可由客户端轮询获取；没有承诺 Firebase 网络投递 exactly-once。
- 生成失败与提交失败有独立失败状态。输入和已执行动作保留；同一请求键重试可继续，不重写已提交回复。

备份升级为 V6，包含上述表及电话回复媒体引用；兼容旧格式时不回填历史回合、不恢复退役的旧记忆/情绪表。
