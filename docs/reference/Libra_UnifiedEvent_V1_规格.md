# Libra UnifiedEvent V1：当前实现说明

> 核对日期：2026-09-17。本文按当前仓库代码整理，描述实际接入方式，不代表运行中的服务已经重新加载这些改动。字段与枚举以 `backend/domains/affect/contracts.py` 为准。

## 1. 用途与边界

UnifiedEvent 用统一结构记录用户消息、生活动态、天气变化等输入，以及定时检查和生成回应的内部触发。

事件被记录不等于一定发消息，也不等于一定调用模型更新情绪。对话按路由决定是否需要 Appraisal；check-in 读取当前状态，检查本身不作为新的情绪刺激。主动联系还需要通过发送条件和 Response Plan。

Need、疲劳和 check-in 中的小红书浏览结果都不是独立事件来源。Need 和疲劳作为检查时的状态输入，工具结果保存在当前轮上下文中。

## 2. 七字段结构

| 字段 | 当前含义 |
| --- | --- |
| `event_id` | 根据来源、稳定来源 ID、事件类型生成的确定性 ID |
| `source` | 事件来源，见下一节 |
| `subject` | 事件主体 |
| `event_type` | 来源下允许的事件类型 |
| `description` | 非空的事件描述文本 |
| `occurred_at` | 发生时间，统一输出为带时区的 UTC ISO 时间 |
| `scope` | `instant` 或 `ongoing`；默认 `instant` |

`subject` 允许 `user`、`libra`、`relationship`、`environment`、`world`。当前主要生产入口使用前三种中的 `user`、`libra`，以及 `environment`；允许 `world` 并不表示仍存在 world_simulation 来源。

当前主要入口使用 `scope=instant`。`ongoing` 是契约允许值，不能据此推断已经接入持续事件生命周期。

ID 生成规则：

```text
key = SHA256(source + ':' + source_id + ':' + event_type) 的前 32 位十六进制字符
event_id = 'evt_' + key
```

`source_id` 是构造参数，`source_key` 是存储或上下文中的关联信息，都不属于这七个字段。相同来源、来源 ID 和类型得到相同事件 ID，用于幂等记录。

`description` 超过 20000 字符时，会截取前 19950 字符并附加截断提示。原始消息仍通过来源记录关联。时间缺省为当前时间；无时区时间按运行机器的本地时区解释后转为 UTC。

UnifiedEvent 本体没有 `facts`、`salience`、`related_event_id`、附件或工具结果字段。媒体和工具结果通过关联记录或当前轮上下文提供。

## 3. 来源与类型总表

当前有 **8 个 source、15 种去重后的合法 event_type**。其中 `state_transition` 同时允许用于两个用户状态来源。

| source | 契约允许的 event_type | 当前主要入口实际产生的类型 |
| --- | --- | --- |
| `conversation` | `user_message` | `user_message` |
| `scheduled_checkin` | `scheduled_probe` | `scheduled_probe` |
| `libra_life_state` | `life_event` | `life_event` |
| `user_manual_state` | `internal_state_change`、`state_transition` | `internal_state_change` |
| `user_life_activity` | `activity_started`、`activity_ended`、`activity_updated`、`location_departed`、`location_arrived`、`checkpoint_completed`、`state_transition` | `activity_updated` |
| `weather` | `environment_change` | `environment_change` |
| `habit_reminder` | `habit_due`、`habit_completed` | 两种均有记录入口 |
| `cognition_trigger` | `response_requested` | 缺少对应事件回执时的回应生成兜底 |

用户状态来源中其余合法类型目前没有分别接入主要生产入口，不能把枚举清单当作已实现的触发清单。本轮已核对这两个来源的业务行为，尚未删除这些未使用的合法类型。

## 4. 各来源的实际行为

### 4.1 conversation：用户发来的消息

统一使用 `subject=user`、`event_type=user_message`。消息形式改变描述，不新增 event_type。

| 消息形式 | description |
| --- | --- |
| 普通文字 | `用户发来一条消息：{原文}` |
| 语音 | `用户发来一条语音，内容：{转写文本}；语音情绪识别：{识别结果}` |
| 表情包 | `用户发来一个表情包，名字：{名字}；含义：{含义}` |
| 图片 | `用户发来一张图片，配文：{配文}` |
| 小红书卡片 | `用户分享了一篇小红书，配文：{配文}` |
| 电话中的用户发言 | `用户电话转写（可能有识别误差）：{转写文本}` |

具体规则：

- 缺少配文、表情包名字或含义时省略对应部分，不补写推测内容。
- 语音情绪使用已有识别结果。标签非空、置信度为有限数且在 `(0, 1]` 时才写入；识别失败时不会默认写成“平静”。
- 表情包名字和含义来自现有资源目录；图片作为附件关联，不塞入描述文本。
- 小红书配文取卡片的 `comment`。读取到的正文等内容通过工具结果提供，不提前写入事件描述。
- 当前图片上传和随后输入的配文可能是两条消息。不会回写先前图片事件；回应阶段可以结合图片附件和文字。
- 原始消息、语音转写和小红书卡片数据仍保留在消息记录中，事件描述不替代完整对话上下文。

普通消息使用 `messages:{id}`，电话发言使用 `call_turns:{id}` 作为稳定来源关联。

`assistant_reply` 已删除。左然输出仍保存为消息、通话或内容记录，但不再生成该类型的 UnifiedEvent。

### 4.2 scheduled_checkin：定时检查是否联系

```text
subject: libra
event_type: scheduled_probe
description: 系统检查左然当前是否适合主动联系；检查本身不代表情绪刺激。
```

定时检查到期后进入检查链路；调度时间用于稳定来源 ID，实际开始检查时间作为 `occurred_at`。具体调度间隔取应用配置，不等于主动消息冷却期。

当前执行顺序：

1. 读取双方当前状态、近期聊天、记忆和发送策略，检查是否允许主动联系。
2. 读取左然当前 Need、疲劳、Mood 和 Emotion，形成 `checkin_state`。
3. 允许发送且开启小红书发现时，先由浏览决策选择是否搜索，将真实候选写入当前轮工具结果。
4. Response Plan 联系决策综合这些输入及未完成话题，输出 `should_send`、`reason`、`expression_intent`。
5. 决定发送后才进入回应生成，提交前再检查发送条件。

当前状态、Need、疲劳、近期话题与小红书结果通过上下文提供，不拼入 check-in 的事件描述。浏览决策在最终联系决策之前执行，所以选择搜索不代表一定联系或分享。

当前 Need 阈值来自 `backend/config/need_contact.json`：

| Need | 阈值 |
| --- | --- |
| connection | 0.60 |
| closeness | 0.50 |
| reassurance | 0.10 |
| care | 0.55 |
| expression | 0.35 |

严格大于阈值才计入超阈值程度，计算为 `max(0, (value - threshold) / (1 - threshold))`。决策提示要求其他条件相同时，超出程度越高越倾向主动联系；没有实现固定数值的随机发送概率，也不会仅因超过阈值强制发送。

疲劳作为判断上下文，可以支持休息或寻求亲近等不同选择；缺失时不推测。

超阈值程度最大的 Need 可形成 `expression_guidance.contact_motive`，向最终回应提供主导需求及表达指导。写作侧不直接暴露 Need 数值和阈值。这是当前动机标识，不是“本次发送必然由该 Need 导致”的因果证明。

#### check-in 中接续未完成话题

联系决策读取最近 20 条消息、最近已发内容与记忆上下文，通过 prompt 判断是否存在有明确证据、尚未结束且适合现在接续的话题。满足条件时提高联系倾向，并要求在 reason 中说明依据、在 expression_intent 中明确话题及表达意图。普通未回复消息不自动算未完成话题；已解决、取消、过时、约定时机未到、用户暂时不想聊或近期已追问时，不据此提高倾向。该规则仅用于 scheduled_checkin，不新增事件或话题数据库，不设固定随机概率，不绕过发送限制。

#### check-in 中可选浏览小红书

通过当前发送条件且开启 `xhs_discovery_enabled` 时，check-in 可以先决定是否浏览小红书找话题。

- 浏览阶段根据当前状态、近期聊天、记忆等选择是否搜索，最多提出 3 个查询。
- 实际搜索结果经筛选、去重后，最多保留 8 条候选。
- 结果通过当前轮 `xiaohongshu.checkin_browse` 工具结果提供给联系决策。
- 决策可以分享候选笔记，也可以普通联系或保持沉默；选择的笔记必须来自实际候选且具有 URL。
- 消息保存后，仅当选中笔记的 URL 确实出现在保存内容中，才标记已分享。

没有独立 `content_discovery` 事件或独立发现调度。用户分享小红书仍属于 `conversation`。

### 4.3 libra_life_state：左然首页生活动态

```text
subject: libra
event_type: life_event
description: 左然生活状态更新：{动态的内容}
```

事件依据 `libra_timeline_events` 的 `id`、`occurred_at`、`event` 产生，首页生活动态也读取这张表。稳定关联为 `libra_timeline_events:{id}`。

表中可能提前写入未来动态，因此不会在插入时立即触发。后台检查仅处理 `occurred_at` 已到达的记录，按时间和 ID 顺序推进持久化游标 `libra_life_timeline_cursor`。

首次建立游标时，以当前时间前 5 分钟为起点，避免补发整段历史。之后积压记录可以被处理，但超过 5 分钟的新鲜度窗口不会用于主动播报。

描述只包含对应动态文本，不再传完整生活状态 JSON。状态查询仍可用于到达授权等判断。新鲜的“左然回到了家”或“左然到达了…”动态，还会核对先前行程授权。

生活动态处理仍受主动联系开关、生活状态更新开关、睡眠和模型占用等运行条件限制。

联系决策仅针对 libra_life_state 加入增强指导：在允许发送且不重复时，明显提高主动联系倾向；尤其开始工作、午饭、晚饭和回到家，优先考虑想起用户、分享真实近况和感受、表达惦念。日常分享本身就是联系动机，无需重要事件或用户先提问。此为 prompt 引导，不设固定概率、不强制每条发送，不编造细节、不机械问候，仍遵守冷却、明确边界和既有到达报备授权。

### 4.4 user_manual_state：用户状态改变

```text
subject: user
event_type: internal_state_change
description: 用户状态从{原状态或“未设置”}变为{新状态}。
```

当前入口在用户状态修改时记录，使用修改时间作为来源标识。自习室实际开始专注时也通过此入口同步“专注中”，结束时恢复原状态；仅打开页面不修改。中途手动选择状态后，不再自动恢复。恢复标记保存在本地，支持应用重启；同步失败时仅保留本地显示，不能保证后端立即获知。来源名称暂保留 user_manual_state，但描述不再将自动切换写成手动操作。契约还允许 `state_transition`，当前主要入口没有使用它。

晚安交流后自动进入“休息中”、用户在之后的日历日首次发来消息时从“休息中”恢复“悠闲”，也会记录 user_manual_state / internal_state_change 事件。描述在状态变化后分别补充“晚安交流后自动更新。”或“用户在次日或更晚再次发来消息，自动结束休息状态。”。事件入队时使用更新后的状态上下文；状态未变化不重复记录，不替换当前 conversation 事件，也不额外启动一次主动回复。

当本次状态事件的新状态为“疲惫”“紧绷”“有点累”时，联系决策收到 increased_care 指导：在其他条件相同时提高主动关心倾向，状态变化本身可作为简短陪伴的理由。此规则不设固定随机概率、不强制发送、不绕过硬条件；从这些状态恢复为普通状态不触发加权。

用户状态可以进入上下文，但“忙碌、专注、在路上、运动中、休息中”等状态不再单独作为禁止联系的条件。

#### 状态事件描述示例

| 触发 | description 示例 |
| --- | --- |
| 手动切换为疲惫 | `用户状态从悠闲变为疲惫。` |
| 自习室开始专注 | `用户状态从悠闲变为专注中。` |
| 自习室结束并恢复 | `用户状态从专注中变为悠闲。` |
| 晚安后进入休息 | `用户状态从悠闲变为休息中。晚安交流后自动更新。` |
| 后续日历日再次发消息 | `用户状态从休息中变为悠闲。用户在次日或更晚再次发来消息，自动结束休息状态。` |

自习室结束恢复的目标取实际保存的原状态，示例中的“悠闲”不是固定值。跨日恢复要求当前仍为“休息中”、有有效的 `user_rest_started_at`，且收到真实用户输入；不是到零点或打开 App 就自动恢复。

消极状态增强仅在当前 source 为 `user_manual_state`、描述匹配新状态为“疲惫／紧绷／有点累”时加入联系决策。即使用户持续处于该状态，天气或 check-in 等其他来源也不会自动携带这段专门指导；它们仍可读取状态作为普通情境。

### 4.5 user_life_activity：用户生活动态

```text
subject: user
event_type: activity_updated
description: 用户生活动态报告：{将开头用户昵称统一为“用户”的动态文本}
```

保存用户生活动态时，以对应记录 ID 关联事件，沿用动态的发生时间。新增动态中的用户称呼使用配置的昵称：例如“{昵称}开始学习：{内容}”“{昵称}结束学习：{内容}，本次专注 {分钟数} 分钟”“{昵称}手机开始／结束充电了：当前电量{电量}%”“{昵称}完成了打卡：{名称}”“{昵称}添加了待办：{标题}”“{昵称}完成了待办：{标题}”。首页动态原文保留昵称；构造 UnifiedEvent 时将开头的当前昵称、旧 simple 或“我”统一为“用户”，例如“用户生活动态报告：用户开始学习：数学”。打卡和待办等无主语的标准动态也补上“用户”。自由填写内容不做全文替换，已有历史记录不批量改写。

生活动态进入联系决策时，通过 prompt 要求模型判断是否确实完成事情。完成打卡、完成待办、结束一次学习或明确完成其他事情时，提高主动回应、具体肯定和陪伴的倾向；不设置固定随机概率，也不强制发送。开始活动、新增待办、离开房间、结束充电不按完成处理。未完成、计划、疑问及他人完成也不计入；同一事实已回应时避免重复联系。habit_completed 进入联系决策时使用同样指导，但本规则不新增完成事件的独立联系入口。

当前统一捕获为 `activity_updated`。契约中的开始、结束、出发、到达、节点完成等其他类型，尚未在主要生产入口中分别使用。

以下为传给事件链路的描述；首页动态原文仍使用昵称。

| 动态入口 | description |
| --- | --- |
| 开始专注 | `用户生活动态报告：用户开始学习：{内容}` |
| 结束专注，至少持续 10 秒 | `用户生活动态报告：用户结束学习：{内容}，本次专注 {分钟数} 分钟` |

| 离开以上房间 | `用户生活动态报告：用户离开了{房间名称}` |

昵称规范化只匹配当前配置昵称和代码内的 `simple`、“我”、“用户”等开头文本，不是语义实体识别；历史其他昵称未必能转换。手动内容也会经过同一开头匹配，不做全文替换。

#### 记录与联系入口的区别

- 新动态入库时以数据库记录 ID 捕获事件。同步接口有新增记录时，还从本批输入中选时间最新的一条启动联系评估，并非逐条主动联系。
- 同步传入的动态没有数据库 ID；当前评估入口回退使用发生时间作为来源 ID，与入库捕获使用的记录 ID 不同。因此同一动态可能形成两个事件 ID，代码尚未统一这一点。
- 打卡完成既可能有 `habit_reminder / habit_completed`，也可能经手机生活动态产生 `user_life_activity / activity_updated`。避免重复关心目前主要依靠决策上下文与提示，不是跨来源事实 ID 去重。
- 删除 `todo_reminder` 没有删除这里的新增／完成待办动态。
- 聊天识别“到家、下班、起床”等活动的辅助函数仍在，但当前未发现生产调用入口；其他 App 打开／关闭采集也不是当前有效入口。

### 4.6 weather：天气变化

```text
subject: environment
event_type: environment_change
```

描述由 `infrastructure/weather/awareness.py` 中的确定性格式化函数生成，不调用 LLM 改写。例如：

```text
用户所在区域（{城市}{区县}）天气由晴转为雨，气温从25℃变为22℃，下降3℃。
```

格式化规则：

- 地点来自已配置的位置，不固定为某座城市；相同城市、区县文本不重复拼接。
- 只写本次检测到的变化，可单独描述天气类型变化或温度变化。
- 无旧天气时只写当前天气；无效数值不进入温度描述。
- 信息不足时使用“天气观测发生变化，具体变化信息不完整”等回退描述。

当前运行入口要求开启天气提醒、有位置配置，并在本地时间 08:00 至 24:00 之间检查；两次检查至少间隔 30 分钟。首次观测只建立基线，不直接提醒。

变化检测使用天气类别变化，或至少 1.2℃ 的温差；温度变化内部间隔为 45 分钟，天气类别变化内部间隔为 15 分钟，雷暴、大雨、大雪等严重天气类别可豁免类别变化等待。这些是天气检测条件，与主动消息冷却分开计算。

事件时间是本次检查时间。结构化天气数据仍用于天气上下文和观测记录，只将事件的 `description` 改为自然语言。

注意：描述格式化会过滤无效数值，但上游观测构造仍存在将缺失温度转成 0 的逻辑，不能把格式化行为理解为整条天气链路都已修正缺失值处理。

### 4.7 habit_reminder：打卡提醒与完成记录

#### habit_due

```text
subject: user
event_type: habit_due
description: 今晚提醒时仍未完成的打卡项目：{项目标题，以“、”连接}
```

当前有效入口在本地时间晚上 20:00 后检查当天未完成项目，描述最多取前 8 项。来源 ID 由日期和标题列表摘要组成；相同列表重试复用事件，列表变化可以产生新事件。

`habit_due` 通过硬性发送条件后，直接确定 `should_send=true`、`reason=habit_due_required`，不再让模型判断是否愿意联系。

发送与重试规则：

- 没有未完成项目时，将当天标记为已处理。
- 尝试前安排 10–15 分钟后的重试时间。
- 失败或没有成功保存可发送内容时，之后再次检查当天最新的未完成项目并尝试。
- 每次生成尝试使用独立轮次标识，避免重复命中此前失败或被抑制的轮次。
- 消息成功保存后即结束当天提醒重试；之后推送失败不会重复生成已保存的提醒。
- 到下一天不继续补发前一天的提醒。

“必须发送”仍以允许发送和生成成功为前提，不绕过睡眠、明确拒绝联系等硬条件。

#### habit_completed

```text
subject: user
event_type: habit_completed
description: 用户完成打卡：{项目标题}
```

打卡保存、同步及相应完成操作可以记录事件，使用习惯 ID 与打卡日期关联。

保留普通事件处理方式，不加入 `habit_due` 的强制发送分支。当前完成捕获入口主要负责写入事件；不能据此承诺每次完成都会单独启动主动联系。如果进入联系决策，仍判断是否需要联系。

### 4.8 cognition_trigger：回应生成兜底

```text
subject: libra
event_type: response_requested
description: 程序请求生成回应（以下是输入上下文，不是新的外部事实）：{当前输入上下文}
```

准备生成回应时，如果无法取得当前输入所关联的 UnifiedEvent 回执，就构造此事件用于统一上下文。这是内部兜底，不是新增外部事实，也不是独立的定时主动联系来源。

保留这个来源，避免没有对应外部事件的生成入口缺少统一事件上下文。

## 5. 主动联系的发送条件

事件记录、状态处理、联系决策、回应生成和消息保存是不同步骤。具体入口还可能有各自的功能开关、模型占用检查和时效条件。

当前主要硬条件包括：

- 左然处于睡眠状态。现有发送策略中的睡眠限制也会影响直接回复。
- 主动联系未开启，或当前主动联系策略禁用。
- 当前边界文本或有效指导命中“不要／别／不许……联系我／打扰我／发消息”等明确拒绝模式。实现使用正则匹配，不等于完整语义识别。
- 最近 3 分钟内存在用户活动，处于主动联系保护期。
- 当前主动联系仍处于冷却期，且不属于豁免提醒。
- check-in 命中静默退避。

生成后提交前还会复查：主动开关是否关闭、是否出现新用户消息、是否进入睡眠，以及适用的到达授权是否有效。输出为空、无效或生成失败，也不能形成实际发送。

**用户忙碌等首页状态不是硬条件，所有来源均不应仅因该状态阻止联系。** 状态仍可以帮助决定表达方式和内容。

### 5.1 主动消息冷却

| 当前联系入口 | 通常最短间隔 | 左然工作中 |
| --- | --- | --- |
| check-in、天气等其他主动联系 | 20 分钟 | 40 分钟 |
| 左然生活动态 | 15 分钟 | 18 分 45 秒 |
| 打卡提醒 | 豁免此项 | 豁免此项 |

相关入口共用 `last_proactive_sent_at`。这是相对上次成功主动发送的最短间隔，不是定时发送周期。

提醒豁免当前按 `habit_reminder` 来源识别；“强制发送”则进一步限定为该来源下的 `habit_due`，两者条件不同。

### 5.2 check-in 静默退避

当前时长为 **40 分钟**，只用于 check-in，打卡提醒不受此项限制。

记录条件是：轮次具有主动联系策略、Response Plan 原本决定发送，但提交时最终没有可发送内容，且触发来源为 `scheduled_checkin`。此时写入 `last_generic_proactive_silence_at`。

模型直接决定不联系，并不自动写入这个时间。因此不能把当前实现描述为“每次 check-in 沉默后都等待 40 分钟”。

### 5.3 联系倾向增强的实际实现

增强规则集中在 `backend/application/contact_decision.py`，通过按条件追加 prompt 引导联系决策 LLM，不是数值概率、随机抽样或硬编码必发。

| 当前输入条件 | 附加指导 |
| --- | --- |
| `libra_life_state` | 明显提高分享近况、想起恋人和表达惦念的倾向，尤其开始工作、午饭、晚饭、回到家 |
| `user_manual_state` 的新状态匹配疲惫／紧绷／有点累 | 添加 `user_state_contact_hint`，提高温柔关心倾向 |
| `user_life_activity` 或 `habit_reminder / habit_completed` | 请模型判断是否真正完成事情；确认完成后提高回应、肯定和陪伴倾向 |
| `scheduled_checkin` | 基于近期对话与记忆检查未完成话题，适合接续时提高联系倾向 |
| 上下文包含 `checkin_state` | 根据 Need 超阈值程度增强联系动机，结合疲劳、情绪和心境判断 |

生活动态、完成事项和未完成话题的专门指导只在对应来源中出现，不会自动复制到所有来源。工作、用餐和回家是生活动态 prompt 中的重点示例，没有单独数值权重。完成事项和未完成话题由模型依据输入判断，没有新增独立的完成事实或话题追踪表。

先检查 `delivery_policy.can_send`，不允许时直接返回，不调用联系决策模型。允许时，`habit_due` 走单独必发分支；其余来源由模型输出 `should_send`、`reason`、`expression_intent`。选择发送后，最终回应依据获批的表达意图生成；这些倾向指导不是无条件追加给每次对话的最终写作 prompt。

## 6. 已停用的来源与类型

| 已移除项 | 当前处理方式 |
| --- | --- |
| `conversation / assistant_reply` | 左然输出保存为业务记录，不生成回应事件 |
| `libra_internal_state` | Need、疲劳移入 check-in 状态判断，无独立冲动触发 |
| `todo_reminder` | 该来源下的待办提醒和完成事件入口停用；待办功能及 user_life_activity 中的待办动态保留 |
| `content_discovery` | 小红书主动发现移入 check-in 的可选工具步骤 |
| `world_simulation` | 停止对应事件的定时生成与启动时相关记忆回填；历史数据和部分辅助代码可能保留 |
| `tool_result` | 工具结果写入当前轮 `tool_results`，不再生成 UnifiedEvent |
| `calendar` | 日历变更不再生成 UnifiedEvent；日历存储、同步和查询保留 |

工具执行仍保留操作记录、已验证结果及完成回执等机制，供决策和回应引用。删除事件来源不等于删除工具能力。

历史兼容：情绪事件处理器遇到旧 `assistant_reply`，或以上已退休来源的待处理事件时，将其提交为跳过，结果标记 `skipped=retired_event_type`，不调用相关模型，也不更新情绪状态。历史记录不会因此被删除。
