# 聊天按需查询

普通用户聊天通过 `application/main_chat_agent.py` 在主聊天模型、同一持久会话中运行。
模型可直接按聊天格式回复，或输出 JSON `calls`，由程序执行白名单只读工具后，
将真实结果送回同一会话继续生成。不是新建辅助决策线程，也不是原生 MCP 工具接入。
稳定人设、近期对话和基本上下文沿用原聊天机制。
工具执行复用 `application/chat_research.py`，每轮最多两个只读调用、最多三轮查询。
若第三轮仍执行工具，再续接一次仅允许最终回复的调用，确保最后的结果被看到。
不会先调用辅助模型决定是否查询。启用并行情绪时，即使无需检索，也需要
先输出 `emotion.await`，接收结果后续接主模型生成回复，通常至少两次主模型调用。

支持个人记忆检索、共同经历检索、角色语料检索、当前状态、当前天气、小红书搜索与笔记读取。
`shared_history.search` 查询个人线和卡面的既定过去；原作往事、书名和剧情细节优先查此库。
多次查询的场景与来源去重合并，并进入原有来源使用记录。搜索默认返回摘要；
`shared_history.read` 允许读取本轮搜索已返回的 `excerpt_ids`，核实全名、原话等摘要未包含的事实。
它只读取数据库中的绑定片段，不能访问任意文件或未检索到的来源。内部查证不要求在回复中整段引用。
重复查询不再立即结束循环，而是回传重复提示，允许在剩余轮次内改为读取原文或换词查询。
回复约束明确要求精确事实有证据，不能沿用先前未经证实的助手回复或自行补全名称。
记忆与角色语料不再每轮固定检索；可以换词补查。同一工具和查询不重复执行。
当前天气工具不支持预报或自选地点。小红书搜索保持仅限用户明确要求搜索的提示约束；
补读的笔记链接必须来自用户输入或本轮搜索结果，程序拒绝未观察到的链接。

情绪评估和需求更新由 `ChatEmotion` 在独立工作线程执行，与主聊天处理并行，
使用当前输入和已有状态的隔离副本；它不写聊天回复，也不并发修改主线程上下文。
聊天情绪处理由独立的情绪 Agent 决定下一步，最多三次决策：`finish`、`appraise`、`need_update`。
每种评估操作最多执行一次；允许直接保持状态，或评估后认定没有变化，不再固定每条消息都跑两种评估。
决策读取当前事件、近期对话、目标标准、当前状态及已有评估结果。
情绪和需求变化仍通过原有 schema、数值边界、单写者租约、事件去重和原子提交；
保持状态也会记录有效互动时间，并保留自然衰减。无效决策不会被当作“无需处理”提交。
`emotion_agent` 在事件和聊天 Trace 中保存动作、简短依据和结果，不输出给用户。
主模型最终回复前调用 `emotion.await`，在工具边界等待完成，再接收状态与语气参考。
主线程后续检索到的记忆不回灌重跑本轮情绪。记忆检索内部的相关性筛选仍保留。
等待结果后由主线程重新生成最终回复，不拼接或润色已有文字。
提前输出的回复不会发送；查询预算用尽时程序也确保先等待再请求最终生成。
等待失败或超过 300 秒时明确标注降级，只提供之前的状态；迟到的工作线程不会覆盖
已经交付的本轮上下文。状态存储仍使用原有情绪事件的去重与事务机制。
写信、相册、日历等写操作仍由
原有授权和执行边界控制，不向查询循环暴露写工具。输入保存、去重和消息交付不变。

决策错误或查询失败时保留已取得的证据，允许生成回复，不假装查询成功。
每轮决策、查询回执和停止原因保存在 turn context 的 `chat_research` 字段；
合并后的记忆与角色证据在交付前登记到原有来源目录。查询轮数增加可能增加等待时间；
每个主线程调用沿用聊天模型的超时设置，三轮限制并不代表整个请求的固定秒数上限。
`chat_research.mode=main_thread` 和 `session_id` 标识执行模式与共享线程；
中间调用计入 `user_chat_tool_step`，最终回复计入原来的 `user_chat` 使用记录。
`emotion_gate` 记录处理状态、主线程接收状态、情绪处理耗时与实际阻塞等待耗时，Trace 页面单独展示。

覆盖测试：`backend/tests/test_chat_research.py`、`backend/tests/test_main_chat_agent.py`；聊天交付与重复请求回归：
`backend/tests/test_turn_pipeline.py`。
